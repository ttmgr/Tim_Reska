How an out-of-memory abort let a single request run code on PHP servers

24 October 2026, Security note

Two critical flaws in the PHP interpreter allow unauthenticated remote code execution on web servers. PHP fixed them on 21 October 2026 by removing the jump-based out-of-memory abort and resetting request-owned state; a third, unpatched flaw followed on 23 October.

Summary

PHP is the server-side language of 69.3% of websites whose language is known (W3Techs 2026), so a flaw in its interpreter is reachable on a large share of the web. On 21 October 2026, the PHP project fixed two such flaws, CVE-2026-109618 and CVE-2026-109619, which allow an unauthenticated attacker to execute code on a PHP web server and are both rated 9.2 under version 4.0 of the Common Vulnerability Scoring System (CVSS) (PHP 2026c). This post describes their mechanism, the fix, the exploitation observed so far, and the versions that remain exposed.

First, both flaws arise when a fatal error, typically an out-of-memory (OOM) error, aborts a request while request memory is partially initialized or still referenced from global state, so that cleanup code or the next request on the same worker operates on invalid memory. Second, the fix replaces the immediate jump out of the interpreter with a delayed abort at a consistent point and resets a wider set of request state, while no configuration change can replace the update. Third, exploit attempts were recorded four days before disclosure, and at least 7.8% of PHP websites run a major version for which no fix exists.

Mechanism of the two flaws

PHP ends a request that exceeds its memory_limit by calling longjmp(), which returns control to an earlier point in the program and skips the code that would otherwise leave request memory consistent (PHP 2026a). In CVE-2026-109618, the failing allocation occurs while request memory is already reachable but not yet initialized, so request shutdown later reads or frees memory that may still contain attacker-controlled data from earlier allocations (CERT-EU 2026). Since the failing allocation need not be related to the corrupted memory, any sufficiently large input can trigger the error. Multipart upload parsing provides such input, as multipart requests without a usable declared length pass the initial post_max_size check, a single part may carry an unlimited number of headers whose in-memory size exceeds their transmitted size, and empty file controls create metadata arrays without counting toward max_file_uploads. The PHP security team validated a full remote exploit against Apache with mod_php under default limits, whereas the susceptibility of PHP-FPM, FrankenPHP and LiteSpeed (LSAPI) rests on source analysis only.

CVE-2026-109619 is a use-after-free in which error, session, object or extension state held by a persistent worker continues to reference memory of a previous request (PHP 2026b). Such stale state arises when a fatal error, for example a parse failure, an uncaught error, a failed require, an execution timeout or an OOM error, interrupts the reset of that state. Operations that run before normal request initialization then consume it, including warnings raised while INI settings are applied (even when errors are neither displayed nor logged) and the handling of session upload progress. Wiz Research reported concrete variants, among them a backtrace pointer (EG(last_fatal_error_backtrace)) that is not cleared after an OOM error and a session identifier (PS(id)) left pointing to freed memory, which returns reclaimed heap contents to the attacker in the PHPSESSID cookie (Tzadik et al. 2026). The same report states that every PHP version released in the last decade is affected by at least one of the issues, although this has not been independently confirmed.

Discovery and disclosure

Wiz Research identified the first flaw on 19 August 2026, confirmed unauthenticated code execution against Drupal and WordPress on 20 and 21 August, and reported the findings to the PHP security team on 24 August (Tzadik et al. 2026). After PHP acknowledged the reports on 21 September, a coordinated fix was prepared, and Linux distributions and long-term support vendors received the patches in advance (PHP 2026c). The planned disclosure on 22 October was preempted when details appeared on social media on 20 October (watchTowr 2026), and PHP released the fixed versions one day later (Figure 1). Wiz states that the work combined its Wiz Atlas tool with the models Gemini 4 Argon and GPT-5.6 Sol, and attributes contributions to discovery, exploit development, attack detection and patch validation to Gemini 4 Argon. While the advisories credit four reporters (lcfr-hax, sagitzadik-wiz, tomash-areion and amyb-oai), the relative contribution of the models and of the human researchers cannot be determined from the public record.

The fix

The patch for CVE-2026-109618 removes longjmp() from OOM handling (PHP 2026a). A request that exceeds its memory limit now raises a delayed soft OOM error at the next safe point of the virtual machine, where request state is consistent, so shutdown no longer encounters partially initialized memory. Should memory use reach a second, higher threshold before that point, the process terminates immediately via _exit() and skips shutdown altogether, which preserves the memory limit as a protection against resource exhaustion. The patch for CVE-2026-109619 resets a wider set of request-owned state, since this state "must not survive into operations that precede normal initialization" (PHP 2026b), although the advisory does not itemize the code changes. In both cases, the update takes effect only after every PHP worker has been restarted, because running workers retain the previous code (watchTowr 2026).

Exploitation

Amazon honeypots recorded an exploit attempt on 17 October, four days before disclosure, and Cloudflare observed attempts rising from tens of thousands within 45 minutes of the 21 October release to millions by early 22 October (The Hacker News 2026). While watchTowr reported exploitation against its honeypot network on 21 October (watchTowr 2026), Sophos and Arctic Wolf described failed attempts to install a Mirai botnet variant, and Wordfence and others reported scanning without confirmed code execution (The Hacker News 2026). These figures derive from a news report that cites the vendors and require validation against the vendors' own publications. As of 22 October, neither CVE was listed in the Known Exploited Vulnerabilities catalog of the US Cybersecurity and Infrastructure Security Agency (CISA) (watchTowr 2026).

Exposure and interim measures

Among websites that run PHP, 65.4% use PHP 8, 26.8% PHP 7, 7.7% PHP 5 and 0.1% PHP 4 (W3Techs 2026; Figure 2). Since PHP 7.3 and older receive no fix, at least 7.8% of PHP websites run a major version that cannot be patched, and PHP 7 installations can be patched only on 7.4 through a minimal source backport or a vendor package (PHP 2026c). PHP 8.2 reaches its end of life on 31 December 2026.

PHP states that no configuration change makes an installation safe and lists measures that only reduce exposure to the demonstrated attack paths (PHP 2026c). For CVE-2026-109618, these comprise an administratively enforced memory_limit=-1, a post_max_size of 8M without uploads or 32M with uploads, and a container or cgroup memory limit in place of RLIMIT_AS or RLIMIT_DATA, since the latter cause mmap() to fail and thereby trigger the vulnerable code. For the same reason, memory_limit=-1 remains incomplete, as a failed mmap() can still reach longjmp() (PHP 2026a). For CVE-2026-109619, PHP recommends session.upload_progress.enabled=0 in php.ini or the FPM pool followed by a restart of every worker, and fatal_error_backtraces=0 on PHP 8.5, whereas ini_set() and .user.ini apply too late in the request, and hiding diagnostics with error_reporting, display_errors or @ has no effect.

A third vulnerability

On 23 October, PHP disclosed CVE-2026-115560, a further code execution path that the 21 October releases do not close (PHP 2026c). Its preconditions are uncommon, since an application must configure session.serialize_handler as php_binary or php_serialize, switch it to php with ini_set() before session_start(), and keep session upload progress enabled. PHP therefore defers the fix to the next regular release and recommends session.upload_progress.enabled=0 until then, the same setting already advised for CVE-2026-109619. No exploitation of this flaw had been reported by 24 October (The Hacker News 2026).

Conclusion and open questions

PHP2Shell indicates that an abort mechanism designed for resource control can leave a persistent interpreter in an inconsistent state, and the fix removes this condition at its origin by moving the abort to a point where request state is consistent. Several questions remain open. The full advisory for CVE-2026-115560 is pending, an exploit against PHP-FPM has not been demonstrated, and the 7.8% of PHP websites on PHP 5 and older have no upstream remedy. The share of the discovery attributable to the language models named by Wiz also remains undetermined.
